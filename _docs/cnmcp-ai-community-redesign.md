# CNMCP AI 相关开源社区重构设计

状态：已对齐。本文只记录产品与架构决策。
范围：不改应用代码、数据库迁移、`package.json` 或配置；下文的实施顺序留到后续变更。

品牌与域名保持 **CNMCP / cnmcp.com**。产品从「中文 MCP 目录 + 机器验证」扩展为面向 **AI 相关开源** 的中文社区。社区表面对齐 HelloGitHub 已有的发现、搜索、筛选、详情、提交/分享、评分、评论/体验、点赞、收藏和个人页。对象仍限于 AI 相关开源，不是泛开源。MCP 是二级类型之一；只有这个类型才挂动态验证。

## 1. 背景与目标

### 现状

CNMCP 现在是中文 MCP 资源目录和机器验证平台，不是 UGC 社区。目录按业务场景收录 MCP；静态检查看公开来源、工具声明和仓库状态；具备条件时做 MCP `initialize` 与 `tools/list`，stdio 在隔离容器里探测，并保留变更记录。配置体检在浏览器本地完成，不上传配置。

代码在现有 monorepo：

- `apps/web`：Next.js 站点，经 OpenNext 跑在 Cloudflare Workers 上
- `apps/api`：Cloudflare Worker，公开 API、提交、队列、D1、Cron；证据对象可放 R2
- `packages/schema`、`packages/checkers`、`packages/doctor`：共享结构、静态/动态检查、浏览器端体检

运营内容走私有 CMS `cnmcp-server`。它服务运营，不是社区主流量路径。

现有 D1 以 `servers` 为中心（并含 `vendors`、`pricing`、`endpoints`、`verifications`、`tools`、`score_snapshots`、`change_events`、`submissions`、`ingest_state`、`server_sources`、`declared_tools`、`server_configs`、`server_readmes`、`static_checks`、`github_repository_state`、`stdio_probe_runs`、`resource_identities`）。这套表描述的是 MCP 服务，不是可评分、可收藏的开源项目。

### 目标

做成 HelloGitHub 那样的中文社区，范围只放在 AI 相关开源：skills、agents、MCP、教程、软件，以及插件和 skill/MCP 管理工具等。插件和管理工具在起步分类里先归入「软件」，需要时再加类型。

第一阶段的产品表面按 HelloGitHub 社区能力做齐，不把收藏、点赞、评论留到以后：

- 发现：首页信息流（最新 / 热），可按业务分类、项目类型、安全状态筛选
- 搜索：关键词，并叠加两级分类
- 详情：元数据、分类、安全摘要、评分、评论/体验、点赞、收藏、分享
- 提交/分享：粘贴 GitHub 地址，可写一段推荐语，自动入库后出现在列表里
- 个人页：我提交的、我的评分、评论、点赞和收藏夹；公开收藏夹可被别人打开

数据量仍按**数百个项目、较低 DAU** 设计。这只约束容量和推荐复杂度，不用来砍社区功能。

技术栈不换：仍是这个 monorepo 里的 Next.js 与 Cloudflare Workers / D1 / Queues。`cnmcp-server` 继续承担运营内容、分类维护、下架和改标签。

### 旧数据与切换

线上目前没有真实用户。按绿场做彻底重构，不为旧数据负责，也不为「站点不能空」做过渡。

明确不做：

- 迁移旧 `servers` 及相关表
- 为了供给保留旧 MCP 目录的只读快照
- 新旧站并行、双读，或给旧链接做连续性跳转

空站上线可以接受。旧库停用或删除即可，它不是新产品的数据源。表名若和现有 `submissions` 等冲突，换一个新的空 D1，或清空后重建。这是为了新模型干净，不是为了留一份旧目录。

## 2. 决策记录

| 决策 | 备选 | 原因 |
| --- | --- | --- |
| 做 AI 相关开源社区，社区能力对齐 HelloGitHub | 泛开源的 HelloGitHub 克隆；或功能砍半的目录 | 对象仍是 skill、agent、MCP、教程、软件等；互动方式按 HelloGitHub 已有社区能力做齐 |
| 保留 CNMCP / cnmcp.com | 新品牌、新域名 | 扩展名字的含义，已有域名继续用 |
| 路线 A：在现有 monorepo 里重做领域模型 | B：新社区应用 + 旧验证服务并存；C：先用静态页做运营 | 一套栈；安全检查和社区放在一起；旧数据可以丢 |
| 绿场重构。旧 `servers` 数据与线上连续性都不做 | 迁移旧目录，或冻结一份只读目录供访问 | 线上没有真实用户，空站可以接受 |
| 安全：所有项目都做线索收集和静态扫描；动态检查只在类型为 MCP 时做 | 所有类型都做完整动态检查；或有风险就不允许上架 | 先上架。`pending` 是还没查完，不是有风险 |
| 提交：自动拉取 GitHub 后上架，有问题再下架 | 先人工审核再上架 | 冷启动要快 |
| 登录只做 GitHub OAuth | 微信登录，或允许匿名写入 | 对象是开源项目，GitHub 身份足够 |
| 第一阶段包含 HelloGitHub 的社区表面：发现、搜索、筛选、详情、提交/分享、评分、评论/体验、点赞、收藏夹、个人页 | 先只做发现和评分，收藏和点赞以后再做 | 不以缩小版验证社区；只把和 AI、安全焦点无关的编辑产品、个性化推荐留在外面 |
| 两级分类：一级是业务领域，二级是项目类型 | 只用 skill / agent / mcp 这种平铺标签 | 先按场景找，再按形态筛。MCP 的动态验证只挂在类型 `mcp` 上 |
| 容量按数百个项目 | 按 1 万级目录设计 | 用不上的规模不做（YAGNI）。这不表示砍掉收藏和评论 |
| 继续 Next.js + Cloudflare；CMS 仍是 `cnmcp-server` | 换一套技术栈 | 复用现有部署、队列和检查器 |

## 3. 非目标（第一阶段）

第一阶段不做：

- 旧 `servers` 数据的迁移、只读快照、双读，以及为现站连续性做的任何保留
- 微信登录，以及匿名评分、评论、点赞、收藏或提交
- 月刊 / 月报、热点周刊、讲解栏目。这些是编辑产品，不是要对齐的社区互动；运营稿仍可走 `cnmcp-server`
- 个性化推荐、用户关注关系、等级和网站徽章
- 新品牌或新域名

浏览器端配置体检（`packages/doctor`）留在仓库里，但不进入社区入库主路径，也不作为第一阶段交付。

点赞、收藏夹、评论/体验、个人页都在范围内，不再后置。

## 4. 信息架构

公开站点以项目为对象。运营文章、公告仍可以由 `cnmcp-server` 提供。发现、详情、搜索、提交、评价和收藏不依赖 CMS 才可用。分类名单由 CMS 维护，站点只读这份名单。

| 路径 | 作用 |
| --- | --- |
| `/` | 信息流。可切换最新、热，并叠加一级业务分类、二级项目类型、安全状态（`pending` / `clear` / `warn` / `risk` / `scan_failed`）。只出 `listed` 项目 |
| `/categories/[slug]` | 某个业务领域的项目。页内再用类型筛选 |
| `/projects` | 全部项目。同一套分类、类型、安全状态筛选 |
| `/projects/[slug]` | 详情：元数据、一级分类、二级类型、安全摘要、评分、评论/体验、点赞、收藏、复制链接分享。类型为 `mcp` 时多一块工具列表和探测结果 |
| `/submit` | 已登录用户提交 GitHub URL，可附推荐语。自动入库后即为 `listed` |
| `/search` | 关键词搜索。可同时限定业务分类和项目类型 |
| `/login` | 仅 GitHub OAuth |
| `/me` | 个人页：我提交的、我的评分、评论、点赞、收藏夹（含私有） |
| `/u/[login]` | 公开个人页：公开提交、公开评论、公开收藏夹 |
| `/collections/[id]` | 一个收藏夹。私有的只有主人能看 |

详情上的安全摘要始终可见，证据默认折叠、可展开。`pending`（还在检查）和 `scan_failed`（没跑成）都要写成未完成，不能用风险样式。`taken_down` 不进信息流和列表；直接打开旧链接时说明已下架。这里的「旧链接」指本站项目被下架后的地址，不是旧 MCP 目录的历史 URL。

热度由 Cron 做粗排（例如近期评分数、点赞和收藏），不按人推荐。没有项目的一级分类不出现在默认筛选项里，名单本身仍保留，运营可改。

写入（提交、评分、评论、点赞、收藏）都要 GitHub 登录。只读页面不要求登录。

## 5. 两级分类

分类是两级，不是一串平铺标签。自由标签可以用，但不能代替这两级。

一个项目有一个主业务分类，可选少量次分类；有一个主项目类型。筛选用主分类和主类型。次分类只让项目也能在那个领域下列出来。

### 一级：业务领域

热门 AI 应用场景。下面是起步集合，**可改**。上线后由 `cnmcp-server` 增删改排序，不写死在前端。

| 起步分类 | 大致覆盖 |
| --- | --- |
| 程序开发 | 写代码、改代码、审查、工程自动化 |
| 视频创作 | 生成、剪辑、字幕、分镜 |
| 游戏开发 | 游戏制作、资产生成、NPC 与玩法 |
| 图像与设计 | 画图、海报、界面与视觉 |
| 写作与内容 | 文章、脚本、翻译 |
| 音频与音乐 | 语音、音乐、播客 |
| 办公与效率 | 文档、表格、会议、邮件、知识整理 |
| 数据分析 | 表格分析、指标、可视化 |
| 研究与知识 | 检索、论文、知识库 |
| 教育与学习 | 讲解、练习、课程辅导 |
| 营销与客服 | 增长文案、社媒、对话客服 |

这 11 个是起点，不是冻结枚举。空分类不放进导航和默认筛选。

### 二级：项目类型

挂在每个业务领域下面，全站共用同一组类型。起步集合同样可增补：

| 类型 | 含义 |
| --- | --- |
| skill | 可安装的技能或技能包 |
| agent | 智能体，或可运行的智能体配置 |
| 教程 | 教程、文档、课程型仓库 |
| 软件 | 可运行的应用、插件、管理工具 |
| mcp | MCP 服务 |

不要把「视频创作」这类领域写进类型。插件和 skill/MCP 管理工具先放在「软件」；真要单列时再加类型，而不是另起一套一级分类。

### 列表、搜索和筛选怎么用

筛选条件可以叠加，互不代替：

- 只选一级：`/categories/视频创作` 或 `/?category=视频创作`，列出该领域下全部类型
- 只选二级：`/?type=mcp`，列出所有领域里的 MCP
- 两级一起：视频创作 × mcp，只看这个领域里的 MCP
- 搜索：`/search?q=字幕&category=视频创作&type=软件`
- 安全状态是第三条筛选项，加在信息流和列表上，不替代分类

未推断出分类或类型的项目仍然 `listed`，标成未分类。它们出现在「全部」里，不出现在某个具体分类页，直到提交者或运营改对。

提交者和运营都可以改主分类、次分类和类型。改成 `mcp` 时补做动态检查；改离 `mcp` 时详情不再展示工具列表和探测结果，已有扫描记录留着。

### 和安全的关系

线索收集和静态扫描对所有项目都做。动态验证、工具列表、探测记录只在类型为 `mcp` 时挂上。其他类型不做 MCP 握手。

## 6. 领域模型

新表服务社区，不从旧表导数据。用新的迁移在空库上建 schema。可以直接停用或删除旧库。不为用户保留旧目录的只读入口。

### `categories` 与 `project_types`

- 一级 `categories`：slug、名称、说明、排序。对应上一节的起步名单，运营可改
- 二级 `project_types`：slug、名称。起步为 `skill`、`agent`、`tutorial`、`software`、`mcp`
- 只有 `mcp` 这个 slug 打开动态验证

### `projects`

一个 GitHub 仓库对应一个项目。

- `slug`：站内稳定标识
- `repo`：规范化的 GitHub 仓库（owner/name 与 URL），用作去重键
- 主 `category`，可选次分类
- `type`：二级类型。暂时判不准时为空（未分类），仍然上架
- `tags`：自由关键词，可选
- `summary`：来自仓库元数据的短介绍；提交推荐语可补在摘要旁，不覆盖仓库事实
- `status`：`listed` 或 `taken_down`

项目状态只表示是否公开。安全结论不写进这个字段。

### `users`

- GitHub 用户 id、login、avatar
- 不存微信身份，也不建匿名写用户

### `ratings`

- 一个用户对一个项目最多一条
- 星级，外加可选短评

### `reviews`

评论和体验文用同一套记录。短评论可以只有正文；体验文带标题。

- 标题（可选）、正文、所属项目、作者
- 第一阶段不做楼中楼，也不做用户关注

### `likes`

- 一个用户对一个项目最多一个赞

### `collections` 与 `collection_items`

- 收藏夹属于用户，有标题，可公开或私有
- 收藏夹里是项目，同一项目可放进多个收藏夹
- 公开收藏夹出现在 `/u/[login]` 和 `/collections/[id]`

### `submissions`

每次提交一条记录，并留下入库状态（已接收、重复、元数据已拉取、失败可重试、完成）。可带推荐语。重复的 GitHub 仓库不新建第二个 `projects`，只把这次提交记为重复。

### `security_scans`

每个项目在入库时就有安全记录。重扫追加新记录，对外只展示最新一条，旧记录留下供复核。

- `clues`：线索收集结果
- 静态摘要：`pending`、`clear`、`warn`、`risk` 或 `scan_failed`，并带证据
- 动态摘要：仅 `type = mcp` 有探测结论；其他类型为跳过

列表和详情上的安全状态读最新扫描，不读 `projects.status`。

### `mcp_*`（仅 `type = mcp`）

可选扩展，例如工具列表、探测记录。承接现在的握手、`tools/list` 和容器探测。非 MCP 项目不建这些表的行。

旧表（包括现有 `submissions`）不改造成上面的新模型，也不做数据回填。

## 7. 安全入库流水线

原则：**安全展示不挡住上架。`pending` 不是 `risk`，`scan_failed` 也不是 `risk`。**

1. 已登录用户提交 GitHub URL，可附推荐语。按规范化仓库去重，写入 `submissions`。新仓库立即创建 `projects`（`listed`，安全状态 `pending`，分类和类型可先空着）。
2. 队列拉取仓库元数据，推断一级业务分类和二级类型，补上 `summary`。拉取失败仍保持 `listed`，摘要可暂时用仓库名，提交记为可重试；不因没有 README 而下架。
3. 收集线索，写入 `security_scans.clues`。
4. 静态扫描必做，结论为 `clear`、`warn` 或 `risk`，并保存证据。扫描本身失败时项目仍然 `listed`，状态为 `scan_failed`。
5. 动态检查只在类型为 `mcp` 时跑，复用协议握手、工具列表和容器探测。其他类型跳过。类型后来改成 `mcp` 时再入队。
6. 详情把安全摘要放在显眼位置，证据可展开。运营可通过 `cnmcp-server` 改分类、类型、标签，或将项目标为 `taken_down`。提交者也可改自己项目的分类和类型。
7. Cron 定期重扫、重试失败的拉取和扫描，并重算粗热度。MCP 的变更观察（工具清单、仓库状态）只保留在 `mcp` 类型上。

`risk` 默认仍然留在列表里，用摘要告诉读者，而不是自动下架。下架是运营动作。

## 8. 架构切分

```text
apps/web     发现、分类、详情、搜索、提交、登录、评分、评论、点赞、收藏、个人页。OpenNext → Cloudflare Workers
apps/api     公开读 API、GitHub OAuth 会话、接收提交并入队、读写 D1
Queues       ingest → security-static → 仅 mcp 走 security-dynamic / 现有 MCP 探测
packages     schema 描述新模型与两级分类；静态规则走 checkers；MCP 检查器只挂在动态路径
cnmcp-server 运营内容，分类与标签维护，下架。不承载社区主流量
Cron         重扫、粗热度、失败重试
```

会话在 API。Web 负责跳转 GitHub 和展示登录态。

队列按阶段拆开，避免一次消息里串完拉取、静态和动态。MCP 动态阶段调用现有检查能力（远程握手与 `tools/list`，stdio 仍走隔离容器），不把动态检查推广成所有类型的门槛。

证据摘要进 D1。体积大的原始证据可以继续放 R2。不迁移旧的证据对象，也不把旧对象展示给用户。

`packages/doctor` 保持本地体检，不进这条队列。

## 9. 实施顺序

下面是后续实现顺序。**本设计不实现其中任何一步。**

1. D1 新 schema：分类、项目、用户、评分、评论、点赞、收藏、提交、安全扫描。空库，不导入旧表
2. GitHub 入库（去重、建 `projects`、拉元数据、推断一级分类和二级类型）
3. 静态安全（线索 + 静态扫描 + `scan_failed`）
4. 信息流、分类页、详情、搜索，以及两级筛选
5. GitHub OAuth，以及评分、评论/体验、点赞、收藏夹、个人页
6. `/submit` 页面（GitHub URL + 可选推荐语）
7. 把 MCP 动态探测接到 `type = mcp`
8. 文案、空状态、空分类隐藏、下架展示等收尾

第 2 步可以用内部入口或 API 灌入项目；第 6 步再对登录用户开放提交页。这样列表不需要等提交页才能验。灌入的是新项目，不是旧 `servers` 行。

## 10. 假设

- 继续当前 monorepo 布局：`apps/web`、`apps/api`、`packages/*`，不新建平行应用。
- 线上没有真实用户。旧数据和现站连续性不在范围内，绿场可以接受，包括一段空站。
- 数据量按数百项目、低 DAU。社区功能按 HelloGitHub 已有能力做齐，不因此改成缩小版。
- MCP 验证是类型 `mcp` 上的增强，不再定义整站。
