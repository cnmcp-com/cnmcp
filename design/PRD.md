# CNMCP 产品需求文档 · 定稿

版本：2.0 · 2026-11-17 · 面向普通用户的 MVP。

## 直接执行

### 1. 定稿依据与目标

以 [最终交互原型](prototype/README.md)的最终确认布局为依据，收敛为普通用户版本。本文完整替代此前追加式 PRD；旧版父子节点、全部混排、左侧标签、运营体验均不再适用。

**帮助用户围绕一个领域的目标，找到可尝试的做法、相关开源资源和真实使用反馈。**

用户可以先描述需求，也可以直接寻找工具。社区允许提问、方法分享、选型比较、失败复盘和新发现，不要求每篇帖子都是完整方案。统一发布对象叫“主题”；主题与资源是两个独立积累单位，通过引用连接，互不隶属。

首批领域为视频、游戏；视频覆盖 AI 视频制作涉及的模型、Skill、工作流、剪辑和自动化。资源以开源及开放生态为中心，普通 HTTPS 新链接也可建档，许可未知时明确留空，不把商业链接或开放权重伪称为开源软件。

### 2. 用户、权限和范围

| 用户 | 可执行操作 |
| --- | --- |
| 访客 | 浏览领域、概览、主题和资源，搜索、查看公开引用与评论，使用本机最近浏览 |
| 已登录普通用户 | 发布主题、开放式回复、资源评论、收藏、关注主题、反馈“有帮助”、举报/纠错、保存草稿、查看自己的工作台和通知 |
| 内容作者 | 在上述基础上编辑自己的主题并补充后续反馈，不获得其他用户内容的管理权 |

首版通过 GitHub OAuth 登录。稳定 GitHub 用户 ID 映射到独立的站内账号，站内内容和互动归属该账号。首版开放普通用户身份，原型的体验登录使用本地演示账号。

**P0 包含**网站读写闭环、全站搜索、普通用户登录、资源引用建档、基础资料同步、互动、站内通知、侧栏和本机历史。

**P1 单独交付** MCP 公开检索、经用户授权的订阅管理与增量读取。原始 MCP 目标保留，不以本轮文档或演示页面假装已上线。

**本版不包含**运营后台、分类管理界面、举报处理台、资源审核、认证等级、质量总分、积分、广告、工具执行、模型托管、邮件/Webhook 推送、跨设备浏览历史。举报仅提供普通用户提交和自己的提交回执。底层可见性状态是读取保障，不构成运营功能需求。

### 3. 信息架构与分类

| 维度 | 规则 |
| --- | --- |
| 固定栏目 | 全部、主题、资源发现；位于 Logo 同一行 |
| 领域 | 全部、视频、游戏；用于主题和资源的浏览范围，不是节点父级 |
| 主题节点 | 全站平级、可在多个领域适用；每个主题恰好一个领域、一个节点 |
| 资源标签 | 全站唯一、配置领域适用关系；资源可多领域，各领域可多标签 |

| 节点 | 视频 | 游戏 |
| --- | --- | --- |
| 求方案、方案分享、问与答、批处理 | 可用 | 可用 |
| 脚本与分镜、素材生成、视频剪辑 | 可用 | — |
| 玩法与关卡、引擎开发 | — | 可用 |

首发 2 个领域、9 个节点、13 条领域节点关系；不复制两份“问与答”。首发 9 个标签、14 条领域标签关系：工作流、批处理、本地运行、ComfyUI、Python 在两领域可用；视频生成、字幕、分镜只用于视频；游戏引擎只用于游戏。

领域与节点/标签使用连续白色导航。没有“领域、浏览、节点”前置说明列；不放左侧标签栏。主题节点与资源标签复用同一种水平文字链接样式，视觉统一不改变其数据模型。

### 4. 三个栏目

| 栏目 | 内容与数量 | 可见筛选 | 深入入口 |
| --- | --- | --- | --- |
| 全部（默认） | 最近讨论最多 6 条；资源发现最多 3 条，独立分区，均按最新创建排序 | 只有领域 | 更多主题、更多资源；保留领域并清除分类 |
| 主题 | 连续主题列表，展示领域/节点、作者、时间、引用及独立回复数 | 领域 + 节点 | 主题详情；最新/活跃排序，待回应状态，分页 |
| 资源发现 | 连续资源列表，展示用途、类型、领域/标签、Star 与站内互动 | 领域 + 标签；保留类型和排序 | 统一资源档案；无页内搜索框 |

概览没有混合信息流、双重分类筛选、统一排序或分页。旧链接附带的节点或标签不得暗中缩小概览；入口生成干净领域 URL，服务接口只接受领域条件。

主题默认“最新”按创建时间降序；“活跃”按最近有效主题回复/正文更新活动排序，以 ID 稳定打破同时间平局。待回应表示没有任何可见回复，不是同级栏目。资源默认按讨论引用、评论、收藏、有帮助依次降序；可切换 GitHub Star 或最新发现。Star 缺失排在已知值之后，真实 0 与未知 NULL 分开。

切换栏目保留领域。切换领域时仅保留仍适用的节点/标签，否则回到全部节点/不限标签；原型不隐式换成另一个具体节点。进入概览以及概览的“更多”入口时清除分类。领域改变不能复制资源或评论。

### 5. 关键页面与普通用户流程

| 页面 | 定稿要求 |
| --- | --- |
| 主题详情 | 领域/节点面包屑、标题作者、正文、收藏/关注/分享/反馈、作者编辑与后续反馈、提及资源汇总、开放式回复 |
| 资源详情 | 统一名称和来源、用途、运行/许可说明、带来源时间的 Star、独立评论、引用主题、资料纠错；默认显示独立评论 |
| 发布/编辑 | 标题、选填正文、预览与引用工具、单选领域/节点、发布和私有草稿；连续表单，不新增内容类型或主题标签 |
| 全站搜索 | 顶部唯一常驻入口，按当前领域搜索主题与资源；结果分组/切换，零结果可携带搜索文字发主题 |
| 工作台 | 我的收藏、关注主题、我的主题、我的回复、草稿、我发现的资源；只读取本人私有关系 |
| 通知 | 自己的全部/未读通知、跳转相关内容、单条和全部已读；已不可用内容不泄漏正文或旧标题 |
| 设置 | 普通账号信息、浅色/深色、退出；原型另保留“重置本地演示数据”说明，不提供角色切换 |
| 指南 | 普通用户的分类说明、引用和交流规则；不包含运营使用指南 |

访客尝试写入时进入登录；登录完成继续原操作，返回地址限定站内路径。生产使用安全会话和服务端所有权校验，按钮隐藏不能替代鉴权。普通用户无权编辑其他作者主题或直接修改全站分类/资源资料；纠错通过反馈提交。

#### 发布与草稿

- 标题 4–100 字；正文可空，最多 12,000 字；作者后续反馈最多 4,000 字。
- 公开发布必须有有效领域节点组合；草稿允许领域/节点不完整，有节点则必须有对应领域。
- 发布页领域改变时，有效共享节点保留，专用节点不适用则清空并提示，不替作者选节点。
- 草稿保存、正文预览不创建公开引用，不贡献资源热度。
- 作者编辑只更新自身主题；使用版本校验避免旧页面覆盖新内容。失败保留输入，冲突返回后允许重新确认。
- 本版不增加公开主题/回复删除操作；删除草稿和取消收藏/关注为已有用户操作。底层软删除字段用于生命周期完整性。

#### 回复、评论与引用

回复不分“求解、方案、经验”等类型。主题回复和资源评论均必填，1–4,000 字，各自独立计数；引用回复只允许同一主题内，资源评论引用评论只允许同一资源内，界面保持平铺。

编辑器通过 @ 或按钮搜索站点资源，插入稳定资源 ID 链接；直接粘贴本站链接、GitHub 或 HTTPS 链接也可识别。支持中文输入、键盘选择、Esc 关闭、预览和无结果状态。

公开提交时服务端解析链接：命中既有来源则复用资源；未知链接立即创建资源及来源，再建立引用并排队补资料。GitHub 常见变体归一到仓库身份，普通 HTTPS 保留语义路径、查询与必要哈希路由。并发提交同源链接不得产生两个档案。

主题正文和其回复引用同一资源，汇总按“主题 + 资源”去重。资源评论引用其他资源不会增加主题回复，也不产生主题采用量。资源评论可附一个相关主题链接，仅用于阅读跳转，不计入该资源的讨论引用。引用表示提及，不表示采用、兼容或完成验证。

### 6. 资源分类与质量

新链接和已有收录都是站点资源，无“已验证资源”、临时资格或资料完成后才能展示的等级。资料采集失败保留资源 ID、原链接和已有讨论。首版优先同步 GitHub 可信 API；其他 HTTPS 先保留来源，不承诺所有外站自动补齐资料。

资源可关联多个领域；每条标签绑定必须同时满足“资源已归属该领域”和“标签适用于该领域”。同一资源跨领域只有一个档案、同一份评论与质量信号。未分类资源在全部领域和直接档案中可见，在具体领域中暂不展示；引用主题不自动赋予资源分类。

本版不提供人工分类后台。首批领域、节点、标签与资源分类通过版本化配置/来源清单初始化；后续采集只补充有明确依据的资料，无法确定的领域与标签保持未分类。新资源暂时只在全部领域出现是已接受的首版边界，不能通过偷偷继承主题领域来掩盖。

| 质量信号 | 定义 |
| --- | --- |
| GitHub Star | 官方仓库快照及时间；未同步为 NULL，非 GitHub 为不适用 |
| 收藏 | 对该资源未撤销的不同用户收藏关系；主题收藏单独保存 |
| 评论 | 该资源可见独立评论数，含有价值的负面意见 |
| 讨论引用 | 可见主题正文或其可见回复引用的不同主题数 |
| 有帮助 | 对可见资源评论的去重有效反馈，可撤销 |

这些事实分别呈现，不生成精确质量总分，不将引用称为采用量。代码许可与模型权重许可分开；未知保持未知。

### 7. 社区右侧栏

| 模块 | 行为与边界 |
| --- | --- |
| 用户信息 | 访客简介/登录/指南；登录后昵称、收藏数、关注主题数、我的主题数、未读通知与设置；数字来自可见内容和本人的关系 |
| 参与入口 | 创作新主题；当前领域等待回应的主题数量，忽略隐藏的节点条件 |
| 今日热议 | 当前领域最多 5 条，当日有可见回复的主题，按当日回复数、主题时间、ID 降序；旧主题有今日回复也可入榜 |
| 最近浏览 | 实际打开的主题/资源；按类型+ID去重、最近访问置顶；保留 20 条、显示最新 5 条，跨领域保留 |

生产“今日”统一采用站点时区 Asia/Shanghai，由服务端计算 UTC 秒级边界；不按主题发布时间代替回复发生日，不计隐藏、过期或未来时间的回复。原型的已知示例回复按预览会话模拟日期并明确标记“演示”，生产不保留这条模拟规则。

没有热议时显示空状态及待回应入口，不用历史回复充数。最近浏览不预填数据，保存在当前浏览器，刷新保留，可清空；隐藏或不存在的目标不展示。首版不建服务端浏览历史表，不向 MCP 输出本机历史。账户退出保留本机历史，用户可单独清空，界面明确本机范围。

所有标准页面复用侧栏；详情页专属上下文模块附后。桌面位于右侧，780px以下移至主列表下方，520–779px可两列、手机单列；内容和操作保持可达。

### 8. 关注、通知与反馈

主题关注在网站内只有一份关系，工作台和侧栏计数一致。取消关注停止未来通知，不删除主题或已收到的通知。

新回复通知作者和事件发生时的关注者，排除操作者本人。同用户同一事件只产生一条通知，同时命中作者和关注时以直接回复原因优先。关注和取消关注均记录当时的事件水位。取消前已发生的回复仍可异步投递，重新关注后从新的水位开始。资源引用反馈仅在有明确接收者时产生。

通知与内容写入可靠衔接：先持久化事件，后台任务幂等生成通知。通知只向接收者开放，读取时重新检查目标可见性。普通用户能提交内容反馈并拿到回执，PRD 不包含处理人、处理台或运营审计要求。

### 9. 视觉与交互规范

沿用定稿的灰白底、蓝色操作、紧凑连续列表；最大 1120px 容器、248px 侧栏、18px 间距、5px 模块圆角及系统中文字体。顶部三栏目与 Logo 同行；领域和分类无明显中间切割。全站搜索保留，资源页不重复放搜索。

手机上栏目和全站搜索换行、分类自然换行；弹窗焦点可见且支持 Esc，正文和引用不横向溢出。空、加载、失败、未登录、不可用状态保留可继续的操作。资料同步状态不充当质量等级。

### 10. 数据与两项目职责

[数据库设计](database/README.md)定义全新空库基线，覆盖用户、会话、分类、主题/回复、资源/评论/来源/引用、互动、草稿、关注/订阅、事件、通知、反馈及基础任务。普通用户表没有管理角色，浏览历史留在本机。

[项目架构](ARCHITECTURE.md)规定：cnmcp 负责网站和公开接口契约；cnmcp-server 负责唯一业务服务、数据库、鉴权、资料任务与 MCP 入口。网站及 MCP 共用同一业务层和数据，不各自维护资源目录。

### 11. MCP 阶段边界

P1 先提供公开内容检索、主题/资源详情、资源反向引用和分类列表。公开工具不返回草稿、会话、举报、通知和个人收藏。

登录用户授权后才提供自己的订阅创建/查看/撤销及事件增量读取。条件覆盖领域、平级节点、领域+节点、主题、资源和关键词；不引入另一套用户或资源 ID。标签订阅、邮件、Webhook 不在首批；HTTP MCP 的授权不能直接复用 GitHub 登录凭据或网站会话作为第三方 Bearer Token。

订阅是条件持久化加游标拉取，不承诺客户端离线时主动收到推送。授权、令牌生命周期及保留窗口在 P1 接入前单独验收，当前不声称生产 MCP 已实现。

### 13. 交付与上线状态

当前已交付可交互本地前端、定稿 PRD、数据库设计/查询/测试及架构方案。原型中的账号、发帖、通知及热议属于本地演示；生产 OAuth、API、采集、可靠通知、MCP 及远端部署尚待实施。新增登录和幂等表是设计及验证结果，不代表服务已接入。

不保留旧业务表和旧数据，不设计兼容迁移；也不因获得重构授权就自动清空远端数据库。本轮未建生产库、未发布或推送代码。

## 深度交互

先检验“一个具体问题 → 有上下文的回应 → 可尝试资源 → 后续反馈”的闭环。P0 可用现有事实评估主题得到首个实质回复的比例、作者后续反馈和资源新增独立讨论；收录量和 Star 不能单独证明社区价值。跨页转化与长期留存需另行定义最小分析，不能用本机历史冒充站点行为统计。

单节点归属仍有语义重叠：具体专题优先具体节点，跨环节分享和综合问题用通用节点。资源分类初期通过配置维护，未分类新链接可能暂不进入具体领域，这是轻量范围的代价。先观察真实使用，再决定是否增加普通用户的分类建议能力；不提前恢复运营后台或双重筛选来填补内容供给问题。
